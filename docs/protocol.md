# Bewpakorn Queue implementation — 2026-11-16

Approved design: ../../outputs/2026-11-16-bewpakorn-extension-design.md. User explicitly authorized implementation; continue without another design approval. New isolated source tree, no existing repository to worktree. Do not modify RAM binary or its live encrypted account file. Final deliverables go under outputs.

## Global constraints

Only explicitly cataloged map-service products; PROCESSING initial status; FIFO createdAt ascending, order ID tie break; scan all pages before selecting. One primary daily button `สำเร็จ`; only that action advances current job, including blocked or preparing. Never change shop status, trade, buy, or submit an order form. No auto start on install/startup. Customer and operator identities separate. Secrets only in transient memory and isolated customer WebView profile; no secret in logs, chrome.storage, reports, ledger or chat. Native RAM sessions stay encrypted. Existing account metadata unchanged. Explicit identity check before ready. Unknown inputs fail closed with actionable Thai codes. Cancellation/generation fences must prevent late import. Challenges remain human-controlled, no bypass or password retry loop. No live customer runs in development.

## Shared protocol (binding)

Native host name `com.bewpakorn.queue`. Frame UTF8 JSON length-prefixed UInt32LE, request max 256KiB, response max 1MiB. Requests `{v:1,id,type,payload}`. Response `{v:1,id,type:'RESULT',ok:true,payload}` or `{v:1,id,type:'RESULT',ok:false,error:{code}}`. Events `{v:1,type:'SNAPSHOT',payload:snapshot}`. No arbitrary URLs, filesystem commands, javascript, or cookie access commands exposed.

Commands:
- `GET_CAPABILITIES` => `{protocolVersion:1,version,webViewAvailable,ramImportSupported}`.
- `GET_ACCOUNT_METADATA` => `{accounts:[{userId,username,alias,description,group,placeId}]}` (no credentials/private server links).
- `GET_SNAPSHOT` => snapshot.
- `RESUME_UNSUBMITTED` payload `{jobId,generation}` only on an intentional toolbar start. Requires current customer.canResume from a pre-fill LOGIN_FORM_TIMEOUT, no persisted submissionAttempted and no importIntent. Retains job/order identity and handled ledger, rotates generation/completion token, revalidates the operator and returns customer waiting. Startup never issues this command.
- `CLAIM_ORDER` payload `{order:{shopId:'bewpakorn.rdcw.xyz',orderId,productId,productName,mapId,mapName,placeId,operatorUserId,createdAt,customerUsername,quantity},protectedOperatorUserIds:[...]}`. All configured operator IDs are protected across maps. Native creates job and starts operator validation. Same order claim returns same current; different while busy rejects CURRENT_JOB_EXISTS. Handled rejects ORDER_ALREADY_HANDLED. Missing operator mapping creates blocked current, never skip.
- `PREPARE_CUSTOMER` payload `{jobId,generation,username,password}`. The list API has no Roblox username: CLAIM_ORDER accepts an empty customerUsername; PREPARE_CUSTOMER binds it once from the freshly read detail. Any later preparation must match the bound username and is never another automatic submission. Refuses operator overlap, fenced cancel. Uses new dedicated WebView2 profile. Validated cookie imported to current RAM via existing receiver, then read-only persistence identity check. Challenge detection events pause submission; allow human manual completion within same context.
- `COMPLETE_CURRENT` payload `{commandId,jobId,orderId,generation,completionToken}`. Atomic handled ledger, closes only owned browser, idempotent replay, rejects stale token. Return snapshot. Do not select next internally. A pre-POST durable importIntent contains only identity metadata, receiver PID/start time and a one-way session fingerprint. Ambiguous network failures retain this intent. Completion returns RAM_IMPORT_UNCERTAIN until the persisted session matches or that original receiver has exited; the extension retains its completion intent for reconciliation. No subsequent import may overwrite an unsettled intent. Alternate known RAM instances fail closed before POST.

Snapshot shape `{revision,current:null|job,handled:[{shopId,orderId,completedAt}],capabilities?:object}`. Job `{jobId,generation,completionToken,order,state:'preparing'|'ready'|'blocked',customer:{username,userId?,state:'waiting'|'preparing'|'ready'|'blocked',code?},operator:{username?,userId?,state,code?},code?}`. Persist no secret. On host restart retain job identity and token; unverified role becomes blocked RECOVERY_REQUIRED, never silently login again. Native named mutex prevents multiple host instances claiming separately.

Extension internal UI messages `{type:'UI_GET'|'UI_START'|'UI_COMPLETE'|'UI_OPTIONS_GET'|'UI_OPTIONS_SAVE'|'UI_ACCOUNTS',payload?}`. UI snapshot `{connection:'connected'|'disconnected',phase:'idle'|'scanning'|'working'|'empty'|'blocked',native:snapshot|null,queue:array,issue?:code,configured:boolean}`. Runtime responses `{ok:true,payload}` or `{ok:false,error:{code}}`. `UI_COMPLETE` must include visible job identity fields, not consult a newer job at dispatch. Broadcast `{type:'UI_STATE',payload:state}`.

Shop module exports async `scanOrders(config)` => array of metadata and `openAndReadOrder(order)` => `{tabId,username,password}` (password transient only). Only extension worker calls it. `scanOrders` must throw rather than claim global oldest if page coverage unknown. Export `defaultCatalog()` and optional `discoverCatalog()` for options. Catalog config `{version:1,catalog:[{productId,productName,mapId,mapName,placeId,operatorUserId}],shopOrigin:'https://bewpakorn.rdcw.xyz'}`. Product names are display only, IDs are eligibility authority.


## v1.1.0 additions — dual clients and operator pools (binding)

`GET_CAPABILITIES` additionally returns `dualClientLaunch:true` and `operatorPools:true`.

`CLAIM_ORDER` order gains `operatorUserIds:string[]` (ordered pool) and `privateServerSourceUserId`. Legacy `operatorUserId` stays as the first pool member for migration and display. `protectedOperatorUserIds` is the union of every configured pool plus the private-source id, so a customer can never be a shop account. Native persists `rotation` per shop+map and selects the next pool member at claim; duplicate claims, resume, reconnect and restarts reuse that selection. All enabled products of one map must share the identical ordered pool and private source.

`LAUNCH_PAIR {jobId,generation}` starts or resumes only the current pair. A fresh customer success may schedule its pair automatically because that order was already started by the user; startup/recovery alone never launches. The native worker validates distinct identities, the source account's canonical saved private destination (same place, single `privateServerLinkCode`), obtains a separate ticket per role and launches operator then customer through the trusted registered protocol. Ownership is the exact ticket in the command line plus process start time; the game log is read only when Restart Manager proves it belongs to the owned PID and process FILETIME.

Snapshot roles add `game:{state:'waiting'|'preparing'|'connected'|'blocked'|'closed',code?,pid?,startTimeUtcTicks?,placeId?,serverInstanceId?}`. `connected` requires an owned, still-running client whose current join sequence is a private-server join for the expected place and account, an accepted network connection, an entered play session, and no later disconnect/teleport/exit marker. The pair is `connected` only when both clients are alive with identical nonempty server GUIDs.

`COMPLETE_CURRENT` cancels pending pair launches and closes only the two clients proven owned by that job (CloseMainWindow, never Kill). Unknown ownership or a surviving owned client keeps completion pending with `PAIR_CLEANUP_UNCERTAIN`/`PAIR_CLEANUP_PENDING`; the order is not advanced.

Roblox allows concurrent clients only while something else owns the named mutex `ROBLOX_singletonMutex`; otherwise a new client asks the earlier one to close (`Received close main window request`). RAM holds that mutex by the same mechanism. The host therefore acquires and holds it on a dedicated thread when no owner exists, reports `external` ownership when another process holds it, and fails the launch path with `PAIR_MULTI_CLIENT_UNAVAILABLE` when ownership cannot be established.
