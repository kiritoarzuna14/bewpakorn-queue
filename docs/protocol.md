# Bewpakorn Queue protocol 1.3.0 — 2026-11-17

Current contract: login-only mode. User opens games, delivers goods and edits website status manually. This supersedes the dual-client documents kept as historical design notes. Production excludes Launch.cs/LaunchTests.cs, game process handling and the live-pair CLI.

Native frames remain protocol v1: UInt32LE byte length + UTF-8 JSON; requests `{v:1,id,type,payload}`; replies `{v:1,id,type:'RESULT',ok,payload? or error:{code}}`; SNAPSHOT events. Request limit 256KiB, response 1MiB. Host accepts only the pinned extension origin and one local host instance.

- GET_CAPABILITIES returns version1.3.0, loginOnly=true, accountSelection=true, undoLast=true, dualClientLaunch=false, ramImportSupported=true, webViewAvailable and grouping policy.
- GET_ACCOUNT_METADATA exposes userId, username, alias, description, group only. Cookies, passwords and private links remain native.
- GET_SNAPSHOT returns revision, current job, handled history, canUndo and historyTarget `{shopId,orderId,needsRestoreOrder}`.
- CLAIM_ORDER accepts allowlisted shop/order/SKU/map/time metadata and protectedOperatorUserIds. New customer source is order; operator source is ram and defaults to the configured first pool member if available. No account rotation or game action. Same order claim returns the existing job; a different current job rejects.
- PREPARE_CUSTOMER `{jobId,generation,username,password}` is allowed only for waiting order-source customer. It binds original order.customerUsername, logs in via isolated WebView2, checks identity and protects own-account IDs before RAM import. Persist intent before POST; verify ACK and encrypted-store persistence. Secrets are transient only. Never resubmit automatically after challenge/failure or on startup.
- RESUME_UNSUBMITTED `{jobId,generation}` is issued only by an intentional toolbar start for a retryable customer failure with no unresolved import. It rotates generation/token and returns waiting, retaining original order identity.
- SELECT_ACCOUNT `{commandId,jobId,generation,role,source,userId?}`: role customer accepts order or ram; operator accepts ram. RAM source validates existing session read-only, never imports. Same identity in both roles rejects. Customer change rotates generation/token and closes only the old login browser. Operator change keeps generation/login browser but rotates completionToken. Mutations reject unresolved import, permit proven settlement, and never alter global settings.
- COMPLETE_CURRENT `{commandId,jobId,orderId,generation,completionToken}` marks extension history handled and closes only the owned login browser. It never changes shop status or closes games. Duplicate exact command is idempotent; stale token rejects. Worker selects next only after ACK. Uncertain import fences navigation until persisted fingerprint matches or original receiver lifetime ended.
- UNDO_LAST `{commandId,expectedJobId,expectedGeneration,expectedLastOrderId,restoreOrder?,protectedOperatorUserIds?}` restores the last handled order with a fresh job/token, removes only that history entry and returns interrupted work to ordinary FIFO eligibility. Empty current uses null identity fields. Legacy history metadata comes from fixed shop GET endpoint with password/notes excluded. Global own-account IDs are validated and protected along with history/current IDs. Same persisted command replays without another pop; stale current/target rejects. Revisit allows PROCESSING/COMPLETED login; other terminal statuses are viewable without automatic credential read.

SELECT_ACCOUNT/UNDO intents are persisted before send. Lost replies replay the same commandId. Definitive native rejection clears only the rejected intent; unresolved imports retain it. The native command ledger records request fingerprint, never passwords. UI disables overlapping mutations and binds commands to rendered job/order/generation/token.

UI messages: UI_GET, UI_START, UI_COMPLETE, UI_UNDO, UI_SELECT_ACCOUNT, UI_ACCOUNTS, UI_OPTIONS_GET, UI_OPTIONS_SAVE. Only extension-origin callers accepted. Snapshot contains both role source/state/username/userId/code fields; ready means session/import verified, not gameplay or fulfilment.

Shop uses fixed tRPC GET endpoints in an owned reader tab. Scan all pages, confirm head/count stability, filter configured ORDER SKUs, sort createdAt ascending + orderId tie break. One owned editor tab is reused in background; no shop mutation. readOrderMetadata returns sanitized validated metadata and revisit=true, falling back to bundled map SKU catalog for disabled-map history. readCredentialForm checks exact ID/variant/time, expected field labels and allowed revisit status. No notes are interpreted as instructions.

Catalog config remains version1 with selected products and optional legacy account pools. protectedOperatorUserIds persists known own IDs independently of enabled maps; saving settings unions old and new protection rather than dropping disabled-map accounts. Per-job selectors do not change this configuration.
